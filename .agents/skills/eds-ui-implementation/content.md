# UI Content Guidelines

## Core standards

All apps and products should use simple, concise, clear, and consistent language for UI and functional copy.

For additional guidance, refer to the Microsoft Style Guide.

## Voice and tone

Voice is our personality. Tone is our mood.

Our voice characteristics are:
- Human
- Informed
- Empowering
- Inspiring

### Use human language

- Write for users with clear, direct wording.
- Be explicit about what is and is not possible.
- Never claim functionality the product cannot deliver.
- Reduce cognitive load with common words and short sentence structures.
- Avoid overly technical words when simpler wording works.
- Use natural, supportive reactions when appropriate.

Example: Congratulations, you configured your first process.

### Clarity and consistency

- Educate users and support decision-making.
- Use the same term for the same concept across the UI.
- Give users the information they need to decide.
- Be helpful, guiding, and supportive.
- Enable discovery and explain what to do next.

Example: To get started, add a user.

## Capitalization

### Sentence case

Use sentence case almost everywhere, including:
- Headers
- Buttons
- Navigation labels

Sentence case improves readability and feels more human.

### Title case

Use title case only for:
- Proper nouns (people, places, and named things)
- Product names (for example, Aspen Process Explorer)
- Unique AspenTech or industry concepts (for example, Power Grid)

Do not capitalize general terms such as email, contact center, platform, or phone number unless the term is an official AspenTech-owned name.

## Grammar and mechanics

### Spelling

Use American English spelling across all products.

### Abbreviations

- Use common abbreviations only when space is limited (for example, table headings).
- Avoid abbreviations in body copy.

Examples:
- Ref. for Reference
- No. or # for Number
- Info for Information

### Acronyms

Avoid acronyms when possible.

Assume users may not know acronyms.

On first use, write the full term followed by the acronym in parentheses.

Examples:
- International System Units (SI)
- Digital Grid Management (DGM)

### Numeronyms

Never use numeronyms such as a11y or i18n.

## Style rules

### Consistent language

Use consistent terminology for similar UI patterns.

Examples:
- Create process
- Create dashboard

### Industry terminology

Use common industry terminology and avoid proprietary jargon.

### User-defined titles

When referring to user-defined names, separate them with quotes.

Example: Delete "Upstream Houston TL210" dashboard.

### Verbs vs nouns

- Use verbs for controls that trigger actions (for example, buttons and menu items).
- Use nouns for labels and titles (for example, tabs, fields, navigation labels, and table headers).

Examples:
- Verbs: Open, Set value
- Nouns: Processes, Home

### Required word choices

- Use Create when creating a new object.
- Use Add when adding an existing object to a list.
- Use Delete when deleting an object permanently.
- Use Remove when removing an item from a display or association without deleting it permanently.
- Use Select instead of Choose.
- In selection menus where no item is selected yet, use Select... (with ellipsis).
- Do not use device-specific verbs such as Touch or Click.

## Specific component content guidelines

### Buttons

- Avoid articles (a, an, the).
- Clearly indicate what happens when the user selects the button.
- Start with a verb, except for common actions such as Done.
- Keep labels concise without sacrificing clarity or user confidence.

### Tabs

- Keep tab labels short (1 to 2 words).
- Use nouns for tab labels.
- Keep labels parallel in parts of speech.

Example: Documents, Images, Downloads.

### Inputs

- Use concise descriptive labels, not instructional labels.
- Move instruction into Help Text. Keep help and error text concise (generally no more than 2 sentences).
- Avoid articles and punctuation in short labels where clarity is preserved.

### Checkboxes

- Keep labels short, parallel, and outcome-oriented.
- Avoid negative phrasing when possible.
- Avoid writing legend plus label as one sentence fragment.

### Radio buttons

- Keep options short (1 to 3 words), sentence case, and logically ordered.
- Keep options consistently formatted and validate at group level.

### Switches

- Label should describe what happens when switched on, not the current state word.

### Tables

- Use clear, descriptive column headers and consistent representation rules (for example, decimals, units).
- Use nouns for header captions.
- Use singular or plural form depending on whether a single value is expected or multiple values.

### Toasts

- Keep Toast text brief, specific, and easy to scan.
- Use Toasts to reinforce the result of a user action.
- Example: "Document saved successfully." "Model run started."
- Body text: Use default text style, avoid repeating title text, and limit to 1 to 2 sentences.
- Full punctuation: Use periods for complete sentences and avoid exclamation points.
- If users need more details or an action on another page, use a Link button
